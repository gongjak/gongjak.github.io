전역 guard를 추가하면 그 스코프의 모든 호출 경로를 확인해야 한다

outbound guard를 도입해 외부 API 호출 경로에 preflight 검사를 추가했다. 그런데 같은 guard가 차단하는 _pre_market hook 호출 경로는 확인하지 않았다. 결과: 매 거래일 08:50에 silent 즉사, 30일간 아무도 눈치채지 못했다.

사고 개요#

Lynceus에 outbound guard를 도입했다. KIS API 호출 전에 preflight 검사를 수행해 거래 가능 상태가 아니면 즉시 차단하는 장치였다.

도입 직후부터 이상한 일이 벌어졌다. 매 거래일 08:50:00.02에 에러가 발생했다. 에러 메시지는 빈 문자열이었다.

2026-06-18 08:50:00.021 [ERROR] market_regime_bootstrap_failed:
2026-06-19 08:50:00.019 [ERROR] market_regime_bootstrap_failed:
2026-06-20 08:50:00.023 [ERROR] market_regime_bootstrap_failed:

로그만 보면 “시장 레짐 bootstrap 실패"다. 원인을 찾지 못한 채 30일이 지났다.

30일 로그 전수 감사에서 실체가 드러났다. outbound guard가 _pre_market hook 실행을 매일 차단하고 있었다.

배경: outbound guard의 preflight 패턴#

outbound guard는 외부 API 호출 전에 다음을 확인한다.

  • 거래 가능 상태(tradable=True)인가?
  • 서킷 브레이커가 열려 있지 않은가?
  • 시스템 모드가 ACTIVE인가?

이 검사를 통과하지 못하면 즉시 예외를 발생시켜 호출을 차단한다.

도입 당시 “외부 API를 호출하는 모든 곳에 적용"했다. 그게 문제였다.

문제: _pre_market은 guard 적용이 부적절한 경로#

_pre_market hook은 장 시작 직전(08:50)에 실행되는 초기화 루틴이다.

  • 장 휴장 여부 확인
  • 시장 레짐 bootstrap
  • 거래 가능 종목 목록 로드

이 루틴은 “거래 상태를 확인하기 위해” 실행된다. 즉, 아직 tradable=True가 아닌 상태에서 실행하는 것이 정상이다.

그런데 outbound guard가 이 경로를 차단했다. tradable=False → guard가 preflight에서 즉사 → _pre_market 실행 불가 → tradable=True로 전환되지 않음 → 다음 날도 같은 일 반복.

# 문제 상황 (의사코드)
async def _pre_market():
    # 여기서 외부 API 호출 시도
    holiday_info = await kis_client.get_holiday_info()  # guard 차단됨!
    
    # 이후 실행 불가
    await _bootstrap_market_regime()

패턴: preflight 임시 해제#

해결책은 guard를 제거하는 것이 아니라, 이 특수한 경로에서만 guard를 임시 해제하는 것이다.

async def _pre_market():
    # guard 임시 해제 후 작업, 완료 후 복원
    async with outbound_guard.suspended():
        holiday_info = await kis_client.get_holiday_info()
        await _bootstrap_market_regime()
    
    # guard 복원 후 정상 상태 전환
    await _set_tradable(True)

이 패턴은 이미 outbound guard 도입 직전 수정한 preflight deadlock(v1.10.134)에서 사용했다. 같은 guard, 같은 패턴인데 _pre_market에는 적용하지 않았다.

왜 30일간 발견되지 않았나#

두 가지 요인이 겹쳤다.

첫째, 에러 메시지가 빈 문자열이었다. str(e)만 로깅하는 코드에서 guard 차단 예외는 메시지 없이 즉사했다. market_regime_bootstrap_failed: 뒤에 아무것도 없는 로그는 “에러 내용 불명"으로 처리되기 쉬웠다.

둘째, 매매 엔진이 다른 경로로 동작했다. _pre_market이 실패해도 엔진이 완전히 멈추지는 않았다. 이전 레짐 상태를 유지한 채로 계속 동작했다. “매매는 돌아가고 있다"는 인상이 “bootstrap 실패"의 심각성을 가렸다.

전수 확인이 필요한 이유#

전역 guard나 middleware를 도입할 때 흔히 하는 착각이 있다.

“이 guard는 외부 API 호출에만 적용된다.”

그런데 실제로는 guard가 차단하는 것은 코드 경로다. 외부 API 호출이 아니라, guard가 삽입된 클래스나 함수를 사용하는 모든 경로.

도입 후 해야 할 질문은 이것이다.

  • 이 guard를 통과해야 동작하는 모든 경로를 열거했는가?
  • 그 중 guard 적용이 부적절한(아직 상태 전환 중인, 또는 상태를 설정하는) 경로는 없는가?
  • 차단됐을 때 silent하게 실패하는 경로는 없는가?

코드 검색으로 guard가 사용되는 모든 호출 지점을 찾아 분류하는 것이 가장 확실한 방법이다.

수정 결과#

수정 후 08:50에는 다음 로그가 찍힌다.

2026-07-07 08:50:00.018 [INFO] pre_market: guard suspended
2026-07-07 08:50:00.341 [INFO] market_regime_bootstrap: BULL (ADL=72.3)
2026-07-07 08:50:00.412 [INFO] pre_market: guard restored, tradable=True

30일간 silent으로 실패했던 bootstrap이 정상 동작한다.

교훈#

  • 전역 차단 장치를 도입하면 그 스코프의 호출 경로를 전수 확인하라 — 특히 상태를 설정하는 초기화 경로는 guard 적용이 순환 의존을 만들 수 있다.
  • “매일 같은 시각 + ms 단위 즉사 + 빈 error” = 내부 차단 시그니처 — 네트워크 왕복 없이 즉시 실패한다는 뜻이다. 외부 원인이 아니라 내부 guard를 먼저 의심한다.
  • 에러 메시지가 비어 있으면 타입을 로깅한다 — type(e).__name__을 병기하면 guard 차단인지 네트워크 오류인지 즉시 구분할 수 있다.
