'KIS 장애'로 오진한 날: 외부 탓 결론 전에 확인해야 할 것들

장중 매매불가가 발생했다. 두 회선으로 교차 검증해서 KIS 서버 장애라는 결론을 냈다. 그런데 두 회선이 같은 공인 IP를 쓰고 있었다. 진짜 원인은 자체 코드 결함 3건이었다.

사고 개요#

2026년 7월 7일 오후, 장중에 매매불가 상태가 표출됐다. 서킷 브레이커가 반복 개방됐고, 매매 사이클이 중단됐다.

현장에서 내린 초기 판정은 “KIS VTS 서버 장애"였다.

근거는 이랬다. kpaean(운영 서버), 청비미니(로컬 서버), mbp-m1(개발 노트북) — 세 곳에서 KIS API가 동일하게 응답하지 않았다. “이중 회선 교차 검증"을 통과한 결론이었다.

이 판정은 틀렸다.

오진의 구조: 세 회선이 같은 공인 IP였다#

세 호스트(kpaean, 청비미니, mbp-m1)는 모두 같은 공유기 뒤에 있었다. Tailscale로 접속하다 보니 각기 다른 IP처럼 보였지만, 외부에서 보면 같은 공인 IP 하나였다.

“이중 회선 교차 검증"이 아니라 같은 IP에서 같은 요청을 세 번 보낸 것이었다.

공인 IP가 다른 진짜 대조군이 없었다. 모든 호스트가 동일한 네트워크 조건에 있었으니, 세 곳에서 같은 결과가 나오는 것은 당연했다.

올바른 검증 순서#

재조사에서 밟은 순서가 이후 기준이 됐다.

1단계: 공지 확인
KIS Open API 공지 페이지에 장애 공지가 없었다. 전면 장애라면 공지가 있어야 한다.

2단계: 같은 호스트에서 다른 서비스 확인
kpaean에서 KIS 리테일 웹사이트, API 포털, naver 모두 정상 응답했다. KIS 인프라 전체가 다운된 것이 아니라 특정 API 포트(9443/29443)만 간헐적으로 블랙홀 상태였다.

3단계: 진짜 타회선 검증 (공인 IP 비교 필수)
스마트폰 핫스팟처럼 공인 IP가 다른 환경에서 테스트해야 의미 있는 대조군이 된다. 같은 공유기 뒤 호스트는 대조군이 아니다.

4단계: 타이밍 분석
KIS API 포트가 장 마감 직후 0.04초 만에 즉시 응답으로 회복됐다. 장중에만 발생하고 마감 직후 사라지는 패턴은 서버 부하 연동형 현상이다. 전면 장애와는 다르다.

5단계: 자체 증폭 설정 감사
같은 포트가 간헐적으로 느려질 때, 자체 코드가 그 영향을 얼마나 증폭하는지 확인한다.

실제 원인: 자체 결함 3건#

재조사로 드러난 원인은 KIS 서버가 아니라 자체 코드였다.

결함 1: httpx connect timeout 60초

KIS API 클라이언트의 connect timeout이 60초였다. 연결이 느려지는 순간 요청 1건이 60초 동안 hang 상태로 커넥션 풀을 점유했다. 풀(20개)이 hang 연결로 채워지면 이후 요청이 전부 대기 → 연쇄 타임아웃 → 서킷 오픈 → 매매불가 표출.

로그에서 정확히 60초 간격 재시도가 반복되는 것이 물증이었다.

# 수정 전: hang 연결이 60초간 풀 점유
client = httpx.AsyncClient(timeout=60.0)

# 수정 후: 빠른 실패 + transport 재시도로 흡수
client = httpx.AsyncClient(
    timeout=httpx.Timeout(30.0, connect=10.0),
    transport=httpx.AsyncHTTPTransport(retries=2),
)

결함 2: sweep에서 NULL user_id 행 제외

장마감 후 미확정 주문을 정리하는 sweep 로직에서 user_id IS NOT NULL 필터가 있었다. 그런데 주문 접수 시점에는 user_id가 기록되지 않는 행이 있었다. 이 행들이 sweep에서 조용히 제외됐고, 미확정 주문이 영구적으로 방치됐다.

# 수정 전: user_id 없는 행 제외
.filter(TradeHistory.user_id == engine_user_id)

# 수정 후: NULL도 포함
.filter(
    or_(
        TradeHistory.user_id == engine_user_id,
        TradeHistory.user_id.is_(None),
    )
)

결함 3: Telegram 봇 시작 실패 = 영구 비활성

Telegram 봇 기동 시 첫 TLS 지연 1회로 초기화가 실패하면, 이후 알림 전체가 silent하게 중단됐다. 장애가 발생해도 알림이 오지 않으니 인지 자체가 지연됐다.

이 패턴은 이미 WebSocket 자동복구(v1.10.136)를 구현할 때 동일한 문제를 해결한 바 있었다. 같은 패턴을 Telegram 봇에도 적용했다.

# 지수 백오프 자가복구
BACKOFF = [10, 30, 60, 120, 300]  # 초

async def _start_telegram_bot_with_retry():
    for delay in BACKOFF:
        try:
            await bot.start()
            return
        except Exception as e:
            logger.warning(f"Telegram bot start failed: {type(e).__name__}: {e}")
            await asyncio.sleep(delay)
    
    logger.critical("Telegram bot failed to start after all retries")

수정 전후 비교#

수정 결과는 다음 날 개장에서 확인했다.

지표수정 전수정 후
KIS 타임아웃79건73건
서킷 오픈6회8회
개별 정지 시간최대 3분(60s×3)최대 30초(10s×3)

실패 빈도 자체는 줄지 않았다. KIS API 연결이 장중에 간헐적으로 느려지는 것은 외부 요인이다. 하지만 자체 코드의 증폭이 제거되면서 매매불가 표출 시간이 3분에서 30초로 단축됐다.

검증 도구 없이 대조군을 만드는 법#

현장에서 타회선이 없을 때는 다른 방법으로 대조군을 만들 수 있다.

  • 스마트폰 핫스팟: 완전히 다른 공인 IP. 간단하고 즉시 사용 가능.
  • curl로 직접 포트 확인: curl -v --connect-timeout 5 https://api.kis.developer:9443/ — 라이브러리 없이 원시 TCP 연결 확인.
  • 마감 직후 재현 시도: 시간 의존성이 있는 장애는 마감 후 동일 조건 재현으로 외부/내부 구분 가능.

교훈#

  • 외부 장애 결론 전 필수 순서: 공지 확인 → 같은 호스트에서 다른 서비스 → 진짜 타회선(공인 IP 비교 필수) → 자체 증폭 설정 감사.
  • “교차 검증"은 공인 IP가 다를 때만 유효하다 — 같은 공유기 뒤 여러 호스트는 대조군이 아니다.
  • 타임아웃은 짧게, 재시도로 흡수한다 — connect timeout을 길게 잡을수록 hang 연결이 풀을 점유해 장애를 증폭한다.
  • “외부 의존 비활성화 = 자동 복구 + critical 알림 한 쌍” — WebSocket, Telegram 봇, 외부 API 클라이언트 모두 같은 패턴이 필요하다.
  • 모르는 것은 먼저 물어본다 — 인프라의 미스터리(공유기 05시 순단)는 운영자에게 물으니 30초 만에 해결됐다(정기 자동 재부팅이었다).

관련 포스트#

  • 연결 타임아웃 60초가 만든 요청 적체: httpx와 KIS API의 함정
  • str(e)가 빈 문자열이었다: httpx 예외가 에러 로그를 3주간 숨긴 사례
