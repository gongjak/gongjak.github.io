str(e)가 빈 문자열이었다: httpx 예외가 에러 로그를 3주간 숨긴 사례

httpx 타임아웃 예외를 str(e)로 로깅했더니 에러 메시지가 빈 문자열이었다. 빈 에러 로그 8,001건은 '아무 문제없어 보이는' 로그로 쌓였고, 그 뒤에 숨은 실제 장애 원인 진단이 3주간 지연됐다.

사고 개요#

Lynceus 운영 시스템에서 30일간 로그를 전수 감사했다. 백엔드 에러 약 10,000건을 집계하는 과정에서 이상한 로그 패턴을 발견했다.

[ERROR] recommender proxy error: 
[ERROR] recommender proxy error: 
[ERROR] recommender proxy error:

에러 메시지가 없다. 빈 문자열이다. 그런데 이런 줄이 수천 건 쌓여 있었다.

감사 결과: 이 빈 에러 8,001건이 3주간 실제 장애 원인의 진단을 가로막고 있었다.

원인: httpx 예외는 str()이 빈 문자열인 경우가 있다#

문제 코드는 이렇게 생겼다.

try:
    response = await client.get(url)
except Exception as e:
    logger.error(f"recommender proxy error: {str(e)}")
    raise

httpx.RemoteProtocolError나 httpx.ReadError 같은 예외는 str(e)가 빈 문자열로 반환되는 경우가 있다.

import httpx

try:
    raise httpx.RemoteProtocolError("", request=None)
except Exception as e:
    print(repr(e))   # RemoteProtocolError('')
    print(str(e))    # ''  ← 빈 문자열
    print(type(e).__name__)  # RemoteProtocolError

repr(e)는 클래스명을 포함하지만 str(e)는 메시지 문자열만 반환한다. httpx의 일부 예외는 메시지 없이 생성되기 때문에 str(e)가 비어 있다.

빈 에러 로그가 만든 오진 체계#

이 빈 에러가 왜 문제였는지는 실제 장애 흐름을 보면 이해된다.

당시 recommender 프록시에서는 stale keep-alive 연결로 인한 RemoteProtocolError/ReadError가 반복 발생하고 있었다. 이 예외가 처리되지 않아 unhandled 500 에러가 됐고, 로그에는 트레이스백이 찍혔다.

그런데 에러 메시지가 빈 문자열이었다. 로그를 훑는 사람 입장에서 “에러 내용이 없다 = 뭔가 이상하지만 파악하기 어렵다 = 넘어가자"로 처리되기 쉬운 패턴이다.

더 심각한 문제는 따로 있었다. 동시기에 _pre_market hook에서 outbound guard가 매일 silent 차단을 만들고 있었다. 그 에러도 빈 문자열로 로깅됐다. 두 에러가 같은 패턴으로 섞여 있으니, 어느 쪽이 진짜 장애인지 구분이 불가능했다.

[ERROR] proxy error:          ← httpx stale connection
[ERROR] proxy error:          ← _pre_market guard 차단
[ERROR] proxy error:          ← httpx stale connection
[ERROR] proxy error:          ← _pre_market guard 차단

8,001건의 빈 에러 속에서 “매 거래일 08:50:00.02에 즉사하는 guard 차단"이라는 패턴을 찾아내는 데 3주가 걸렸다.

수정: 예외 타입을 항상 함께 로깅한다#

# 수정 전
logger.error(f"recommender proxy error: {str(e)}")

# 수정 후
logger.error(
    f"recommender proxy error: {type(e).__name__}: {e}",
    extra={"error_type": type(e).__name__}
)

type(e).__name__을 명시하면 메시지가 비어 있어도 예외 종류를 알 수 있다. structured logging이라면 error_type 필드를 별도로 기록해 집계 쿼리에 활용할 수 있다.

추가로 httpx stale keep-alive 문제를 원천 차단하기 위해 클라이언트 설정도 수정했다.

client = httpx.AsyncClient(
    timeout=httpx.Timeout(10.0, connect=5.0),
    limits=httpx.Limits(keepalive_expiry=4.0),  # stale keep-alive 방지
)

그리고 예외 처리에서 HTTP 상태 코드 매핑도 추가했다.

except (httpx.RemoteProtocolError, httpx.ReadError):
    # stale keep-alive 재시도 (멱등 GET만)
    try:
        response = await client.get(url)
    except Exception as retry_e:
        logger.error(
            f"recommender proxy retry failed: {type(retry_e).__name__}: {retry_e}",
            extra={"error_type": type(retry_e).__name__}
        )
        raise HTTPException(status_code=502)

이 패턴이 나타나는 다른 상황들#

httpx만의 문제가 아니다. Python 예외에서 str(e)가 빈 문자열이 되는 상황은 여러 곳에서 나타난다.

  • httpx.RemoteProtocolError — 서버가 프로토콜을 어겼을 때
  • httpx.ReadError — 연결이 끊어진 채 읽기 시도
  • asyncio.CancelledError — str(CancelledError()) = ''
  • 직접 만든 예외 클래스에서 메시지 없이 raise할 때

로깅 코드를 작성할 때 str(e)만 쓰는 것은 불완전하다. 예외의 타입까지 남겨야 로그가 의미를 갖는다.

교훈#

  • str(e)만 로깅하면 httpx 계열은 빈 문자열 — type(e).__name__을 항상 병기한다.
  • 빈 에러 수천 건은 “이상 없음"이 아니라 “정보 손실” — 로그 집계 시 빈 메시지를 별도 카운트해 모니터링 대상으로 삼는다.
  • “매일 같은 시각 + ms 단위 즉사 + 빈 error” = 내부 차단 시그니처 — 네트워크 왕복 없이 즉시 실패한다는 뜻. 외부 원인보다 내부 guard/preflight를 먼저 의심한다.
