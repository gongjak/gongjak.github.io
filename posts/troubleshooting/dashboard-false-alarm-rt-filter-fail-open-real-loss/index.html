종일 매매 불가로 오인한 날, 진짜 문제는 -123,632원 실손실이었다

오늘 매매가 됐나, 안 됐나#

2026년 7월 6일 오전, 대시보드 신뢰 지수 패널에 completed_trade_unconfirmed_fill 신호가 떴다. 심각도 high였다. “완료 상태지만 체결 수량 또는 체결 가격이 0인 매매가 2건"이라는 내용이었다. 등급은 “운영 중단 권고"였다.

운영자는 종일 매매 불가 상태로 인지했다.

포렌식: 엔진은 멀쩡히 가동했다#

trade_history를 직접 확인했다.

확인 항목결과
엔진 가동09:00 market_open_engine_started → 15:30 정상 종료
당일 체결매수 4건(KB금융, 삼화전자, 진흥기업, 파세코) + 매도 2건(진흥기업, 삼화전자)
신호 대상trade_history id 911, 913 — 매도 placement 감사 행
당일 손익realized_pnl -123,632원

엔진은 종일 ACTIVE였다. 신호는 오탐이었다.

그런데 손익이 -123,632원이었다. 매매가 있었으면 손익이 양수여야 정상은 아니지만, -123,632원은 설명이 필요한 숫자였다.

결함 1 — 신호 오탐: placement 감사 행을 모르는 신뢰 신호#

v1.10.138부터 매도 reconcile은 주문 하나당 행을 두 개 남긴다.

  • placement 감사 행: status=completed, filled_qty=0, filled_price=0 — 매도 주문이 KIS에 접수됐음을 기록하는 행
  • 실체결 요약 행: 같은 order_no, filled_qty>0, P&L 포함

프론트엔드 신뢰 신호(operationalTrust.ts)의 예외 가드 is_pending_fill은 매수 전용으로 작성되어 있었다(v1.10.115 당시 매도 reconcile이 없었다). 매도 placement 행을 보면 “완료인데 체결 0"으로 판단한다. /dashboard/today-result도 placement 행을 별도 건으로 집계해서 매도 2건을 4건으로 이중 계상했다.

매도가 하루에 한 건이라도 나오면 이 오탐이 반드시 재현되는 구조였다.

// operationalTrust.ts — 수정 전
const is_pending_fill = trade.status === 'pending' && trade.filled_qty === 0;
// 이 가드는 매수 pending 전용이다.
// 매도 placement 행(status=completed, filled_qty=0)은 걸러지지 않는다.

결함 2 — RT 필터 fail-open: 상한가 추격 매수#

RT 필터(_check_realtime_filter)는 실시간 가격을 기준으로 갭업·갭다운을 걸러낸다. Phase 107에서 도입됐다.

fail-open 조건이 문제였다. live price가 없거나 stale이면 무조건 통과시킨다.

# 수정 전 — live price 없으면 필터 통과
def _check_realtime_filter(self, ticker: str, base_price: float) -> bool:
    live = self._live_prices.get(ticker)
    if live is None or live.is_stale():
        return True  # fail-open: 데이터 없으면 매수 허용
    gap = (live.price - base_price) / base_price
    if gap > self.gap_up_threshold:  # +3% 이상이면 거부
        return False
    return True

7월 6일 14:26, 진흥기업(002780)의 live price가 없었다. RT 필터가 통과됐다. 엔진의 기준가는 전일 종가 936원이었다. 시장가 매수가 나갔고 실체결 평단은 1,216원이었다. 당일 상한가(+30%)였다.

즉시 손절 기준에 걸려 -88,412원으로 청산됐다. 삼화전자(011230)도 동일한 패턴으로 -35,220원이었다.

live price가 없으면 “데이터가 없으니 지금 갭업 중인지 알 수 없다"는 뜻이다. 통과가 아니라 거부가 맞다.

결함 3 — assume_filled: 체결가 오기록#

매수 주문이 타임아웃되고 취소 요청이 KIS에서 거부되면 엔진은 “체결 간주” 처리를 한다. 이 경로에서 체결가를 기록할 때 주문 기준가를 썼다.

002780 매수 행에 936원이 기록됐다. 실제 체결 평단은 1,216원이었다. 화면에서는 “+20% 매도인데 P&L이 -88,412원"이라는 설명 불가 표시가 나타났다.

수정 (v1.10.141)#

세 결함을 하나의 커밋으로 처리했다.

오탐 수정: placement 행 판별 로직을 백엔드로 이동했다.

# trade_audit.py — 신규
def is_audit_placement(trade: TradeHistory, all_trades: list[TradeHistory]) -> bool:
    """같은 order_no에 filled_qty>0 요약 행이 있는 placement 행인지 판별한다."""
    if trade.filled_qty != 0:
        return False
    return any(
        t.order_no == trade.order_no and t.filled_qty > 0
        for t in all_trades
        if t.id != trade.id
    )

/system/trades/today 응답에 is_audit_placement 플래그를 추가했다. 신뢰 신호와 today-result 집계는 이 플래그가 true인 행을 건너뛴다. 단, 요약 행이 없는 unreconciled placement는 여전히 경보한다 — 실제로 체결 확인이 안 된 경우다.

RT 필터 수정: live price 없으면 KIS 현재가를 직접 조회한다.

# 수정 후
async def _build_rt_filter_inputs_with_kis_fallback(
    self, ticker: str, base_price: float
) -> RTFilterInputs:
    live = self._live_prices.get(ticker)
    if live is None or live.is_stale():
        # live price 없으면 KIS에서 직접 조회
        kis_price = await self._fetch_kis_current_price(ticker)
        if kis_price is not None:
            logger.info("rt_filter_kis_price_fallback_used", ticker=ticker)
            return RTFilterInputs(price=kis_price, source="kis_fallback")
        # KIS 조회도 실패하면 fail-closed: 거부
        logger.warning("rt_filter_kis_price_fallback_failed", ticker=ticker)
        return RTFilterInputs(price=None, blocked=True)
    return RTFilterInputs(price=live.price, source="realtime")

assume_filled 수정: 체결 간주 시 KIS 잔고 평단(pchs_avg_pric)을 체결가로 사용한다.

# 수정 후
async def _assume_filled_price(self, ticker: str, order_price: float) -> float:
    balance = await self._fetch_kis_balance(ticker)
    if balance and balance.avg_price > 0:
        return balance.avg_price  # KIS 잔고 평단이 진실
    return order_price  # 조회 실패 시 주문가 fallback

앞으로 이 신호가 다시 뜨면#

completed_trade_unconfirmed_fill이 다시 뜨면 진짜 사고다. unreconciled placement, 즉 요약 행이 없는 placement다. v1.10.141로 false alarm 가능성은 제거됐다.

RT 필터 fallback 작동 여부는 로그로 확인한다. rt_filter_kis_price_fallback_used 또는 rt_filter_kis_price_fallback_failed가 찍히면 live price 부재 상황이었다는 뜻이다.
