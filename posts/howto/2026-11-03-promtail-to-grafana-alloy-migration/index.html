Promtail 지원은 끝났다, Grafana Alloy로 옮기기

Promtail은 2026년 3월 2일 EOL이 됐다. 옛 계획서대로 새로 깔지 말고, alloy convert로 설정을 옮긴 뒤 positions 경로와 메트릭 이름까지 점검해야 한다.
November 3, 2026 · 5 분
목차
  • 처음 든 생각 — 그냥 Promtail 깔아도 되지 않나
  • 설정은 버리지 않아도 된다 — alloy convert
  • 한 번에 못 옮기면 — Promtail 설정을 Alloy로 그대로 돌리기
  • 변환이 끝나도 확인할 것 — 공식 문서의 한계 목록과 보고서 경고
  • 정리
  • 참고

올해 5월 10일에 홈 관측성 스택 계획서를 써 둔 적이 있다. 로그는 Loki로 모으고, 각 노드에서 로그를 읽어 보내는 수집기는 Promtail로 정했다.

반년 만에 그 계획서를 다시 열어 그대로 깔려다가 멈췄다. 설치 문서를 확인하러 Loki 공식 문서의 Promtail 페이지에 들어갔더니 맨 위에 경고가 붙어 있었다.

Promtail is end of life (EOL) as of March 2, 2026. Commercial support has ended. No future support or updates will be provided.

날짜를 다시 봤다. 3월 2일이다. 계획서를 쓴 5월에 Promtail은 이미 지원이 끝난 상태였다. 계획서 어디에도 EOL 얘기는 없다. 그때 공식 페이지를 한 번만 열어 봤어도 알았을 것을, 이미 끝난 도구를 골라 놓고 반년을 묵힌 셈이다. 이 글은 그 계획서를 어떻게 고칠지 정리한 기록이다. 옛 계획이나 옛 글을 따라 Promtail을 새로 설치하려던 사람, 혹은 이미 Promtail을 돌리고 있는 사람에게 필요한 순서만 적었다.

처음 든 생각 — 그냥 Promtail 깔아도 되지 않나#

처음에는 “EOL이어도 당장 돌아가긴 하잖아"라고 생각했다. 집에서 쓰는 스택이고, 로그만 잘 들어오면 그만이니까.

그런데 공식 문서의 문장이 생각보다 단호했다. Promtail 페이지는 “If you are currently using Promtail, you must migrate to Alloy or another supported client"라고 적고 있고, 앞으로의 기능 개발은 모두 Grafana Alloy에서 한다고 했다. 보안 패치도 더 나오지 않는다는 뜻이다. 새로 까는 도구를 처음부터 지원 끝난 것으로 고를 이유는 없었다.

여기서 용어 하나를 정리해 둔다. Grafana Alloy는 Grafana Labs가 만든 수집기(collector)다. 로그뿐 아니라 메트릭 · 트레이스까지 한 프로그램에서 받아 Loki · Prometheus 같은 저장소로 보낸다. Promtail이 로그 전용 배달부였다면, Alloy는 여러 종류의 데이터를 함께 다루는 배달부다. 설정은 Promtail의 YAML 대신 Alloy 전용 문법으로, local.file_match 같은 블록(컴포넌트)을 이어 붙여 쓴다.

왼쪽과 오른쪽 모두 출발점(노드의 로그 파일)과 도착점(Loki)은 같다. 바뀌는 것은 가운데 수집기뿐이다. 왼쪽의 Promtail 하나가 오른쪽에서는 Alloy 안의 블록 세 개(local.file_match → loki.source.file → loki.write)로 나뉜다. 가운데 화살표는 alloy convert로 기존 설정을 옮겨 간다는 뜻이다.

설정은 버리지 않아도 된다 — alloy convert#

다행히 Promtail 설정을 처음부터 다시 쓸 필요는 없었다. Alloy에는 Promtail 설정을 Alloy 설정으로 바꿔 주는 명령이 들어 있다. 공식 이전 문서에 나온 형태는 이렇다.

alloy convert --source-format=promtail \
  --output=<OUTPUT_CONFIG_PATH> <INPUT_CONFIG_PATH>

공식 문서의 예제를 보면 감이 온다. 아래 Promtail 설정이

clients:
  - url: http://localhost/loki/api/v1/push
scrape_configs:
  - job_name: example
    static_configs:
      - targets:
          - localhost
        labels:
          __path__: /var/log/*.log

이렇게 바뀐다(공식 문서의 예제 출력을 옮긴 것이다).

local.file_match "example" {
  path_targets = [{
    __address__ = "localhost",
    __path__    = "/var/log/*.log",
  }]
}

loki.source.file "example" {
  targets    = local.file_match.example.targets
  forward_to = [loki.write.default.receiver]
}

loki.write "default" {
  endpoint {
    url = "http://localhost/loki/api/v1/push"
  }
  external_labels = {}
}

Promtail의 scrape_configs 하나가 “어떤 파일을 읽을지(local.file_match) → 읽기(loki.source.file) → 보내기(loki.write)” 세 블록으로 쪼개진 것이 보인다. 위 그림의 오른쪽 경로가 바로 이것이다.

변환이 매끄럽지 않으면 진단 내용이 stderr로 나온다. --report=<경로>를 붙이면 진단 보고서를 파일로 남길 수 있다. --bypass-errors로 사소한 오류를 건너뛰고 변환할 수도 있지만, 공식 문서는 그렇게 만든 설정이 원래 Promtail과 다르게 동작할 수 있으니 운영에 쓰기 전에 충분히 시험하라고 경고한다.

한 번에 못 옮기면 — Promtail 설정을 Alloy로 그대로 돌리기#

노드가 여러 대라 하루에 다 바꾸기 어렵다면 중간 단계가 있다. Alloy를 실행할 때 --config.format=promtail을 붙이면, 기존 Promtail 설정 파일을 Alloy가 직접 읽어 돌린다. 변환한 설정을 파일로 저장하지 않고 메모리에서 바꿔 쓰는 방식이다.

이렇게 하면 수집기 프로그램만 먼저 Alloy로 갈아 끼우고, 설정 파일 변환은 나중에 천천히 할 수 있다. 다만 공식 문서도 이것을 “임시 전환 단계"라고 부른다. 여기서 쓰는 --config.bypass-conversion-errors 플래그는 운영 환경에서 쓰지 말라고 따로 적혀 있다.

변환이 끝나도 확인할 것 — 공식 문서의 한계 목록과 보고서 경고#

변환은 best-effort, 즉 “할 수 있는 만큼"이다. 공식 문서 끝의 Limitations 절과, 문서에 실린 변환 보고서(--report) 예시의 경고에서 점검할 것을 골랐다.

  1. positions 파일 위치가 바뀐다. positions 파일은 “각 로그 파일을 어디까지 읽었는지” 적어 두는 책갈피다. Alloy는 이 파일을 다른 곳에 저장한다. 컨테이너 영속 볼륨에 기존 positions 경로만 묶어 뒀다면, 새 위치가 볼륨에 들어가지 않아 재시작 뒤 읽던 위치를 이어받지 못할 수 있다. 볼륨 설정을 새 경로에 맞춰야 한다.
  2. 수집기 자신의 메트릭 이름이 다르다. Alloy가 내보내는 자기 감시용 메트릭은 Promtail과 내용은 비슷해도 이름이 다르다. Promtail 메트릭으로 만든 대시보드나 알람은 새 이름으로 고쳐야 한다. 변환 보고서 예시에도 같은 경고가 나온다.
  3. 설정 파일 밖의 값은 따라오지 않는다. Promtail을 실행할 때 붙인 명령줄 인자(예: -max-line-size)나 환경 변수는 설정 파일에 없으니 변환되지 않는다. 직접 옮겨야 한다.
  4. 트레이싱 설정은 자동으로 옮겨지지 않는다. 이것은 Limitations 절이 아니라 변환 보고서 예시의 경고에 나온다. Promtail에 트레이싱을 걸어 뒀다면 Alloy 문서를 보고 다시 설정해야 한다.
  5. 웹 화면이 다르다. Promtail 웹 UI 대신 Alloy UI를 쓴다. 디버깅할 때 보는 곳이 바뀐다.

내 계획서에는 Grafana 시각화와 알림 항목은 있었지만, 수집기 자체의 메트릭을 보는 대시보드는 없었다. 그래서 당장 2번에 걸리는 것은 없다. 다만 나중에 수집기 감시를 붙인다면 처음부터 Alloy 메트릭 이름으로 만들어야 한다. 계획서를 고칠 때 이 점도 함께 적어 둘 생각이다.

정리#

계획서에서 바꿀 것은 세 줄이다.

  • 로그 수집기: Promtail → Grafana Alloy
  • 기존 Promtail 설정이 있으면 alloy convert --source-format=promtail로 변환하고, 진단 보고서(--report)를 함께 남긴다
  • 변환 뒤 positions 경로 · 수집기 메트릭 이름 · 명령줄 인자를 따로 점검한다

이번 일로 배운 것은 Promtail 자체보다 계획서를 쓰는 습관 쪽이다. 도구를 고를 때 예제나 기억이 아니라 그 도구의 공식 페이지부터 열어 봐야 했다. 앞으로 계획서에 도구를 적을 때는 공식 페이지에서 지원 상태를 확인한 날짜도 함께 적어 두려 한다.

아직 확인하지 못한 것도 적어 둔다. 내 옛 계획의 실제 설정이 alloy convert에서 경고 없이 통과하는지는 아직 돌려 보지 않았다. 위 예제는 공식 문서의 예제다. 실제로 돌려 보면 결과를 덧붙이겠다.
